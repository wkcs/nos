# nk60_v2 开发与验收

<!-- Copyright (C) 2026 NOS contributors -->

GPIO、SPI1/W25Q 与 USB IN 发送已接入[公共驱动框架](DEVICE_DRIVERS.md)；STM32 寄存器与引脚仍由板级控制器管理。

当前微内核增加 `nk60_v2` 实板目标：STM32F401、61 键 ANSI 布局、74HC595 扫描链、USB FS HID、61 颗 RGB 和 W25Q 配置存储。固件不依赖被删除的旧 RTOS/HAL。没有可访问实板，本次交付固件和软件验证；真实 USB 枚举、引脚、电气时序、灯光与掉电实验仍待上板。

可组合灯效及按键行为绑定见 [自定义灯效](NK60_LIGHTING.md)。完整能力与后续扩展接口见 [NK60能力](NK60_CAPABILITIES.md)。硬件依据见 [硬件迁移记录](NK60_V2_HARDWARE.md)，输入语义见 [键盘引擎](KEYBOARD_FEATURES.md)，USB 协议见 [USB 实现](NK60_USB.md)，维护命令见 [服务说明](NK60_SERVICE.md)。[主流项目调研](KEYBOARD_RESEARCH.md) 固定了 QMK、ZMK、KMK、VIA、Vial、TinyUSB 的官方提交和后续工作。

## 构建

```sh
source /workspace/.nos-env/activate.sh
make PLATFORM=nk60_v2 LIBC=minimal BUILD_MODE=normal firmware -j4
# 可选 MPU 配置，独立目录避免覆盖默认镜像：
make PLATFORM=nk60_v2 LIBC=minimal MPU=1 O=out/microkernel/nk60_v2/mpu firmware -j4
```

也可运行 `make nk60_v2_defconfig` 保存本地配置；该配置会改变后续 make 默认平台。输出包括 `nos.elf`、`nos.bin`、`nos.hex` 和 `nos.map`。本目标只支持 `LIBC=minimal`、单核和正常启动，不链接 VFS、shell、glibc 或共享堆。其他平台仍使用原有完整系统配置。

按旧 F401 xC 最小资源配置：64 KiB SRAM、8 MHz HSE、84 MHz SYSCLK、48 MHz USB、USART1 PA9/PA10 115200 8N1、TIM2 1 MHz。内部 Flash **仅前 128 KiB 用于应用**，后 128 KiB 保留。旧 224 KiB 软件范围与 F401 的 128 KiB sector 5 不对齐，不能保护最后 32 KiB；当前链接器与烧录器共同拒绝跨越 sector 5 的镜像。外置 NOR 最后16KiB分为两扇区 NLP 启动计数日志与两扇区键盘配置日志（均4KiB）。未知非空启动日志内容保留并禁用 NLP；首次迁移须备份并确认尾部四扇区布局。

链接时分别限制 Flash、64 KiB SRAM、用户静态区和至少 4 KiB MSP 余量，页池优先对齐。键盘与空闲任务各使用 4 KiB 用户栈，键盘引擎、USB、配置、RGB 缓冲区均为静态有界数据。默认没有 MMU/MPU 硬件隔离；可选 MPU 仍保留当前 NOS 的共享用户静态区与 Flash 可读执行约束，不能称为完整进程隔离。

## 软件验证

```sh
python3 tests/host_keyboard.py
python3 tests/host_usb_keyboard.py
python3 tests/host_nk60_hardware.py
python3 tests/host_nk60_device.py
python3 tests/host_nk60_service.py
python3 tests/test_nk60_flash_tool.py
python3 tests/nk60_firmware.py
python3 tests/qemu_nk60_startup.py
# 含原有三种 MMU 架构、STM32、RV32 和 POSIX 回归：
python3 tests/acceptance.py --include-posix --require-frozen-source
```

Host 检查编译实际引擎/服务/USB/板级源文件，使用注入的 MMIO、SPI NOR、USB host 和 DMA 模型；ASan、UBSan、LeakSanitizer 检查内存错误。QEMU 启动专项将实际 NK60 ELF 放到原版 `netduinoplus2`，只为验证 Cortex-M 用户入口/系统调用/MPU 路径，由 GDB 明确跳过未建模的 F401 时钟初始化。它不是 NK60 外设仿真，不能证明 USB、扫描和 RGB 已实测。其他 STM32 回归也使用原版 `netduinoplus2`，不使用历史 `nos_stm32`。

扫描目标周期为 4 ms；HC595 单帧至少 936 µs，加上系统调用和调度有额外开销。USB 描述符的 1 ms endpoint interval 不代表实测 1 kHz 键盘扫描。`status` 显示扫描过期、队列溢出、USB、Flash 和 RGB 错误。RGB 在未配置/挂起时断电，使用保守软件亮度上限；整板电流、USB-C 接法和 LED 型号仍需测量。

## 烧录与恢复

```sh
python3 scripts/flash_nk60_v2.py --image out/microkernel/nk60_v2/minimal/nos.elf
# 连接有供电的实板与 ST-Link 后，实际执行：
python3 scripts/flash_nk60_v2.py --image out/microkernel/nk60_v2/minimal/nos.elf --execute
```

默认只输出经验证的 SHA256、ELF 分段和 OpenOCD 命令；`--execute` 才访问探针。工具检查 ARM ELF32/Thumb 入口、向量表、64 KiB 栈顶、烧录物理地址/重叠和 128 KiB 擦除边界。采用 `boards/nk60_v2/openocd.cfg`，只写应用扇区并 verify/reset；不 mass erase、不改 option bytes、不通过 USB 接收固件。SWD 使用 PA13/PA14/GND/NRST，UART 与 USB 走各自接口。此脚本尚未连接真实 ST-Link 验证。

## 实板验收顺序

1. 核对 MCU 丝印、8 MHz 晶振、供电、SWD 和原理图；备份内部 Flash、外置 NOR，确认末四扇区的启动计数/配置布局可使用。
2. 烧录并保存固件 SHA256、串口启动日志和 `status`。确认时钟、用户任务、扫描错误计数和外置 Flash 容量。
3. 主机验证描述符、重复枚举、boot/report 协议、6KRO/NKRO、61 键逐键及和弦、PN/FN、媒体键、锁灯和 key-up。Windows/Linux/macOS 分别记录。
4. 反复测试 USB 拔插、reset、suspend/resume、主机背压；保持按键时切层/改键，检查无卡键。用逻辑分析仪测扫描与输入延迟。
5. 物理解锁后改键/宏/亮度，保存并重启；在 NOR 擦除、载荷、提交阶段断电，验证能恢复完整旧/新配置。
6. 确认 RGB 波形、复位低电平、最大电流和挂起电流；故障时应停止 DMA、关灯并保持 USB/输入服务可诊断。

VIA/Vial GUI、组合键仲裁、tap dance、mouse keys、动态录宏、安全 USB 升级及具体无线/分体模块驱动尚未实现。当前 UART 维护接口和有界宏不能冒称这些协议已兼容。

NLP 已经由独立 USB vendor interface 接入，HID 保持 interface0。标准能力、物理解锁与编译/模型验证范围见 [NLP 实现](protocols/nlp/implementation.md)；[主机工具](../apps/nlp-host/README.md) 提供发现、日志和改键命令。UART 仍是维护文本协议。
