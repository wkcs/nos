## ENOMEM（-12）与按实际长度分配

用户在新固件上报告启动存储和 Web 定义查询均返回 -12。定位到服务将8192字节文档上限当作默认分配量：首次默认基础配置、每次只读定义查询和每次创建编辑租约均申请8KiB，基础保存还额外分配一份正文。此前主机测试直接使用系统 malloc，没有设备剩余堆限制，未覆盖这种压力。

新增受限分配器用例先复现旧代码的定义 READ 失败，再验证修复：在键盘引擎初始化后的额外8KiB堆预算、单笔分配上限4096字节下，首次创建/加载默认配置、打开编辑、草稿存在时读取全部配列/action/灯效定义、PATCH扩容、保存启用、新建宏、租约回收、存储错误恢复和只读重启均通过。配置相关额外堆峰值为6805字节，全部已跟踪分配在测试结束时释放；ASan/UBSan通过。该峰值不包含设备任务栈、VFS/LittleFS缓存和其他驱动的真实占用，不是整机RAM峰值。

修复为：编码器支持不写内存的有界长度测量，默认正文和只读定义按实际长度分配；历史对象先查询经过CRC验证的正文长度；草稿按需增长，分配失败保留原字节/长度/版本；基础保存成功后直接移交草稿所有权，不再创建第三份正文。文档8192字节逻辑上限、协议2.0和落盘格式保持不变。新增大小查询、失败扩容回滚及计数编码用例。

## 2026-11-17 NK60 V1 真机 ENOMEM 修复与验证

硬件为 NK60 V1（STM32F401、64KiB RAM）和 ST-Link V2，使用 `board/nk60-v1/openocd.cfg`、OpenOCD/GDB 真实断点与 SRAM dump。只加载 `0x08004000` 起的应用并校对 `.text`；未擦除 bootloader、未格式化 W25Q 文件系统。之前“仅按实际长度分配”的主机模型不包含整机常驻开销，不能证明真机修复，已由本节结果取代。

断点先捕获默认基础正文 2278 字节分配失败，继续定位到 VFS 的 108 字节 dentry 也无法分配。通用 VFS 长期缓存每个不可变版本的 dentry/inode，失败重试又增加缓存；延迟启动的 nShell 也会在释放出内存后占据约 3KiB。因此不能只按说明字符串长度估算整机资源。

本轮处理：

- production keyboard context 从 4888B 降至 1552B，移除旧协议描述/manifest 等常驻副本；action 名称引用只读定义。
- effect entry 从 52B 降至 20B，10 个灯效另省 320B；不改 UAPI 布局。
- 活动基础配置只保留紧凑绑定和参数；默认配置为 12B，完整 2278B 文档不再常驻。
- 对象服务在文件关闭后回收受管理子树的无引用元数据。新增 borrowed-reader guard，覆盖路径系统调用、shell 执行/管道等待/补全、VFS RPC；打开 FD 和挂载点保持引用。真实 LittleFS 回归验证嵌套 reader、打开 FD、回收后重读及 Flash 字节/擦除计数不变。
- V1 键扫栈由 3072 调至 2048，NLK 栈由 6144 调至 5120，均成为 Kconfig 选项；没有缩减灯效图层数、action 参数或宏能力。
- 真实保存成功但旧 CLI RESULT 的 800ms 查询窗会误报超时；C++、Rust、Web 的 RESULT 单独调整为 15 秒，其他请求超时和修改请求不自动重放的策略不变。
