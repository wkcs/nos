## 当前基线与审查证据

- 已有 `out/microkernel/results.json` 记录：ARM、ARM64、RV64 的 MMU 平台，以及原版 QEMU `netduinoplus2` STM32 非 MMU 平台，合计 8 个运行库组合、280 项重复跨平台检查通过。本轮核对记录，没有重新执行完整 QEMU 矩阵。
- 现有测试覆盖基本调度、IPC、VFS、内存、锁、TLS、浮点上下文和部分用户态故障恢复。尚未覆盖长期资源循环、复杂锁依赖、服务重启、映射失败回滚和完整 POSIX 语义。
- 当前默认启动的是验证程序；用户代码和 VFS 静态链接到同一镜像，内核固定创建它们。任务槽共 6 个，其中只有 3 个用于新增任务；IPC 固定使用端点 0；匿名映射每任务最多 4 段，每段最多 64 KiB。
- C 库基线是 ARM/STM32 Newlib、ARM64/RV64 musl 的有限静态适配。STM32 没有启用 MPU。当前没有 SMP、独立 ELF 加载、完整 pthread、动态链接或持久化文件系统。
- 针对真实 `servers/vfs/server.c` 的宿主复现使用系统 C 编译器，替换用户内存辅助函数与系统调用传输，直接调用其服务处理函数。两个数据完整性问题已复现；这不是新增的来宾 QEMU 验证。

## 分阶段实施顺序

### 阶段 0：稳定当前实现，建立可靠回归基线

先修 F01–F07，随后补 F08–F12 的参数检查、生命周期和故障注入。每类修改独立提交，避免把所有修复与架构重写混在一个提交中。

验收条件：

1. 原有 8 个 QEMU 组合全部通过，并新增上述错误路径检查。STM32 始终使用原版 `netduinoplus2`。
2. 加入可重复的资源循环：至少 1,000 轮任务、FD、匿名映射和锁创建/释放；结束后可用对象/页数恢复到基线。STM32 使用较小并发规模，但仍执行重复循环。
3. 公共核心修改执行完整矩阵；架构专属异常测试在相应平台执行。宿主复现不能替代来宾验证。
4. CI 保存代码提交/工作区状态、构建配置、工具链/QEMU/C 库版本、测试集合和日志；单平台测试不能让报告误显示成完整矩阵。远端 GitHub/GitLab 至少实际运行一次。

### 阶段 1：完善微内核对象、权限和服务生命周期

- 将 `core.c` 按任务、调度、IPC、同步和 syscall 分派拆分，先保持现有行为，再演进对象接口。硬件能力查询与访问权限分开。
- 引入统一对象句柄、引用计数和能力表；端点具有独立生命周期和权利，支持按能力授权、转交与撤销。
- IPC 从固定端点 0 扩展为多个服务端点；定义请求/回复关联、超时、取消、对端退出、资源上限和调度优先级传播。
- 建立 init/服务监督职责；VFS 故障通知客户端并可重启，旧请求和旧句柄不能被新服务实例误接收。明确重启后 FD 和数据恢复策略。
- 增加正常运行与自测构建模式；正常镜像启动真实 init/应用，测试专用 `FINISH` 和自检入口仅用于测试配置。
- 固定 syscall 编号、ABI 版本、各架构参数宽度和消息布局规则，为独立构建的应用保留兼容契约。

验收：两个独立用户态服务可以按权限通信；未授权、超时、客户端退出和服务崩溃不会使整个系统停机；正常镜像持续运行。自测镜像继续覆盖现有矩阵。

### 阶段 2：建立可扩展的内存模型与独立应用加载

- 分离进程、线程和地址空间，去掉固定 6 槽、固定数据模板对任务模型的限制；上限仍可由 MCU 配置约束。
- MMU 平台实现内核代码 RX、数据 RW/NX、用户/内核栈保护与显式 TLB 失效；调整共享 libgcc 等辅助代码的归属，避免依赖用户代码区域执行内核辅助函数。
- VMA 支持范围拆分/合并、部分 munmap/mprotect、清零和配额，逐步支持独立栈与共享内存；物理内存从实际平台布局初始化。
- STM32 增加可选 MPU 隔离、栈溢出检测和每任务区域切换。没有 MPU 的配置继续明确使用共享地址空间，MMU API 返回一致的不支持结果。
- 先从嵌入式 initramfs 加载独立静态 ELF，校验头、段、大小、入口和权限；建立 argc/argv/envp/auxv、BSS、堆、栈以及 ELF TLS 初始化。无需等待持久化磁盘才能开发加载器。
- 非 MMU 应用采用可实现的静态/可重定位装载契约，单独说明共享地址空间与执行限制。

验收：ARM/ARM64/RV64 能运行与内核分开链接的 C 应用；非法 ELF 和越界段被拒绝；MMU 下页权限和栈保护有真实故障验证；STM32 按所选 MPU 配置验证，不能把无 MPU 结果称为隔离验证。

### 阶段 3：形成可说明、可测试的 C 库 / POSIX 支持范围

- 先列 API 支持表：完整支持、有限支持、不支持，以及 MMU/非 MMU 差异。
- 完善标准 FD、dup、pipe、目录/stat、文件打开与 unlink 语义，分离单调时间与日历时间。
- 在线程/地址空间分离和对象生命周期稳定后实现线程创建、TLS、退出/join、futex 或等价等待机制，再适配 pthread mutex/condvar；线程取消、信号等按明确子集推进。
- Newlib 补重入结构初始化和正常退出资源清理；musl 补 ELF TLS、线程启动和所需系统调用。先验证当前 4 个平台/库组合，再考虑 ARM musl、更多 Newlib 平台。
- 用独立程序验证 malloc/realloc/free、stdio、目录、文件、errno/TLS、浮点和多线程，并运行选定的 libc/POSIX 测试子集。

验收：应用无需替换标准 C API 即可在已声明范围内运行；不支持操作不返回伪成功。glibc 所需接口范围显著更大，应作为后续独立兼容目标，先稳定 Newlib/musl。

### 阶段 4：设备服务、持久化存储和旧功能迁移

- 增加 IRQ 对象、等待/确认接口、MMIO 能力和 DMA 缓冲区约束，驱动业务留在用户态。
- 先做交互 UART，再做 virtio-blk 块设备和 VFS 持久化后端，补目录遍历、挂载接口和文件生命周期。
- 按新架构迁移 FatFs，然后根据实际应用需求迁移 USB、显示、输入、Lua/LVGL；每个模块都有单独的能力授权和回归验证。
- 建立真实 STM32 的启动、时钟、中断、串口、MPU/栈和内存布局验证，补足 QEMU 模型覆盖不到的硬件行为。

验收：QEMU 中能交互运行应用并持久化文件；设备服务崩溃按明确策略隔离/恢复；真实 STM32 有可重复运行记录。

### 阶段 5：SMP、更多架构变体与规模扩展

- 在单核线程、对象与锁模型稳定后加入 per-CPU 状态、内核栈、运行队列、跨核唤醒、IPI、TLB shootdown 与锁顺序约束。
- ARM/ARM64/RV64 按实际 QEMU 支持加入多核验证；保持单核 STM32 回归。
- 根据产品需求扩展 RV32、其他 Cortex-M、其他非 MMU 平台和 ARM 硬浮点上下文；每个目标提供启动、ABI 和能力差异说明。
- 最后按实际应用需要安排动态链接、信号、fork 或 spawn 扩展、网络和按需分页。交换不是 MCU 或初期内核的必需前提。

验收：多核调度/锁/地址空间压力测试无资源泄漏和权限错误；新增架构不降低既有平台的功能覆盖。不能因“支持 RISC-V”就宣称当前已支持 RV32 或 RISC-V 非 MMU。

## 下一轮建议交付

下一轮限定为阶段 0 的首批工作：

1. VFS 打开失败的事务处理和空洞清零，添加对应 QEMU 回归。
2. 构建参数签名和 C 库链接依赖，确保测试运行的是最新配置。
3. musl 零长度内存操作、64 位参数收窄校验和明确的不支持返回。
4. 锁生命周期、多锁优先级继承、STM32 分配器锁初始化。
5. 执行完整 8 组合矩阵，并加入资源循环与上述负面测试；更新验证报告。

完成这些工作再推进阶段 1。阶段 1 的能力/对象和 ABI 契约是阶段 2 加载器、阶段 3 线程与阶段 4 驱动的共同依赖；SMP 应在单核基础成熟后开展。
