# ESP32 RAM 文件容量与按文件同步

<!-- Copyright (C) 2026 NOS contributors -->

本批扩展C3/S3的RAM文件，并修正fsync的后端选择。已有raw/WL版本2快照格式保持不变；这不是大文件持久化文件系统。

## 预算与回收

ESP VFS共有32个节点，包含初始6个系统节点，单个RAM文件最多8192字节。每节点保留512字节内联存储，更大文件按512字节递增申请内部capability heap；全部额外缓冲共享32768字节预算。该预算不包含节点表、内联区、打开文件表、栈及SDK其它分配，也不是PSRAM/DMA分配器统一。每任务FD仍为11，路径上限仍为64字节。

节点表和文件表在服务启动时一次性分配，任一分配失败均回滚，不报告VFS就绪。文件增长超出配额返回ENOSPC，物理分配失败返回ENOMEM，超出truncate文件上限返回EFBIG；已有数据、尺寸与偏移不因失败增长而改变。写入到文件上限仍可短写，后续写返回ENOSPC。

预算按标准生态profile验证。开发时64KiB预算在S3第六个8KiB文件上遇到连续块不足：总空闲25456字节、最大块7680字节，正确返回ENOMEM。默认改为两平台一致的32KiB，以给任务、stdio和外设留出空间；运行时其他消费者仍可能先耗尽heap，不能把逻辑配额当成物理内存保证。

扩展和稀疏写补零；缩短文件清零被截断范围，再扩展不会读到旧尾部。截断到512字节以内会退回内联区并释放全部额外缓冲，O_TRUNC同样回收；513字节以上的缩短保留容量供后续增长。unlink后仍被打开或dup引用的文件保留缓冲，最后一个引用释放时回收。RAM文件复位后丢失。

只有ESP profile扩容，普通MCU仍为16节点/512字节，Linux兼容profile维持原32节点/8192字节和共享页机制。公共代码修改须跑完整验收。

## 持久格式兼容

raw/WL继续使用版本2、16条记录、每文件512字节，持久挂载根目录占一条记录。ESP创建第17条持久记录在修改命名空间前返回ENOSPC，不等到sync才发现容量不足。RAM节点不会占用快照记录。

扩容后持久节点可落到索引16至31；序列化现在扫描全部32节点并将持久记录紧凑写入原16条磁盘槽，避免只保存前16个内存节点。导入仍接受旧版含空槽的记录布局；没有改变bank地址、CRC、代次、先数据后头的提交顺序或raw/WL物理映射。

FAT尚未绑定ESP profile，大文件持久化、新格式迁移、加密和掉电实板验证仍待后续开发。不能把8KiB RAM上限宣称为Flash文件上限。

## fsync(fd)

原生API新增nos_fsync(fd)，追加VFS操作码50，不改变现有操作码和消息结构。ESP Newlib、musl及glibc网关的fsync进入该接口；musl/glibc的fdatasync采用同样的保守同步。

| 文件后端 | 行为 |
| --- | --- |
| RAM普通文件/目录 | 成功返回0；不操作Flash，不表示复位后保留 |
| 原生快照文件/目录 | 提交所属挂载的完整双bank快照，保留I/O错误；尚非逐文件写回 |
| FAT文件/目录 | 调用FAT同步接口，ESP未挂载该后端 |
| 只读启动归档 | 内容不可变，无需写回，返回0 |
| 控制台、管道、proc | 返回EINVAL |
| 无效/不属于当前文件表的FD | 返回EBADF |

nos_sync及shell sync保留显式卷级语义，没有持久挂载时返回ENOTSUP。stdio fflush仍只提交用户缓冲，持久文件需要另行fsync；O_SYNC仍明确不支持。SDK保留FD区间继续由原始SDK接口处理。

宿主模型验证真实VFS及分配失败、配额、旧布局导入和后端错误，IPC/设备边界是模型。真实QEMU验证经NOS IPC的容量与回收，以及先创建20个RAM文件、再把高索引持久文件提交并独立重启恢复。冻结结果完成后另行补录。
