- 日期：2026-11-02
- 代码基线：`eb07be4`
- 状态：现状审查与方案比较；建议部分待用户评审，尚未进入实现。
- 工作流：superpowers brainstorming → 已批准设计规范 → writing-plans → 分阶段实现与验证。
- 用户约束：允许调整接口并同步迁移全部调用方；本轮验收 IPC 并发正确性和主机多线程测试，真实多核 QEMU 另行验收。

## 1. 结论

当前实现已经有对象级自旋锁和按优先级排队的基础，但缺少覆盖等待、资源交付、超时、关闭及任务退出的统一完成协议。单独给每个模块补锁，无法解决跨模块的任务状态和对象生命周期问题。

建议先建立共用等待/唤醒及生命周期机制，再分别实现有界消息队列、计数信号量、完成事件、位图通知和请求应答 Endpoint。MCU 和 SMP 使用相同语义，存储和调度后端按配置裁剪。

以下问题来自源码检查和明确的路径/交错分析；本次没有编写运行时故障复现测试。现有回归通过不等于这些竞态已经被覆盖。

## 2. 主要发现

### 高：超时与资源交付没有唯一裁决点

位置：`kernel/task/task.c:99`、`kernel/task/task.c:510`、`kernel/ipc/sem.c:151`、`kernel/ipc/notification.c:89`。

`timeout()` 先持任务锁写入 `flag = -ETIMEDOUT`，随后才取得对象队列锁。相反，释放路径先持对象锁摘出等待者，再释放对象锁并调用 `task_resume()`。

一种交错是：释放者已经选中等待者并交付令牌/通知，但尚未 resume；另一 CPU 的超时仍看到任务阻塞，设置超时并将任务入就绪队列；释放者再次 resume。结果可能触发非法状态断言、重复唤醒，或者等待者返回超时而已交付的资源丢失。

`sem_send()`/关闭路径还复用 `task->list` 保存临时唤醒链表；超时或任务删除对同一个节点的操作缺少共同的保护协议。

### 高：Endpoint 关闭遗漏等待回复的请求

位置：`kernel/ipc/endpoint.c:123`、`:166`、`:267`。

请求交付后，客户端进入 `REPLY_WAIT` 并离开发送队列。关闭只遍历发送和接收队列，无法找到这些客户端。无期限调用可能永久阻塞，关闭也没有统一撤销对应的回复关系与 PI 捐赠。

### 高：对象销毁后 Capability 和在途操作仍可持有裸指针

位置：`kernel/ipc/endpoint.c:157`、`kernel/ipc/notification.c:62`、`kernel/cap/cap_table.c:154`。

查找在释放 Capability 表锁前只读取对象指针，不固定对象生命周期。销毁则关闭后立即 `kfree()`。已派生的别名和已通过检查的并发调用仍可访问释放后的内存。句柄 generation 只能检测槽位复用，不能代替对象引用管理。

静态初始化对象也必须与动态分配对象区分，不能统一走无条件释放。

### 高：回复使用未经同步和生命周期保护的任务指针

位置：`kernel/ipc/endpoint.c:351`、`kernel/task/task.c:387`、`:929`。

回复直接检查和修改 `ipc_partner`、`ipc_state`、`ipc_msg`，没有以请求事务为单位同步；客户端超时、任务删除和新请求会与回复竞争。任务回收也没有等待回复引用释放。需要一次性且带代数的回复凭证，并固定在途请求/任务的生命周期。

### 高：消息长度未校验，队列缺少资源上限

位置：`kernel/ipc/msg_queue.c:44`、`:63`、`:118`、`:176`。

发送和接收的 `int size` 未拒绝负数，也没有验证分配大小加法的溢出。负数传入分配/复制的无符号长度转换可能产生异常分配或越界。每次发送都分配堆内存，消息数量和总字节数没有上限。

USB core/HID 使用此队列传递设备事件；逐条堆分配不具备适合中断事件路径的确定时延。重设计必须规定满队列行为和调用方恢复策略，不能只把无界队列换成有界队列后忽略发送失败。

### 中：消息队列接口与生命周期不完整

位置：`kernel/ipc/msg_queue.c:38`、`:118`、`:176`。

`msg_q_remove()` 是空实现。接收绑定单个 owner，首次绑定没有锁保护。接收缓冲区不足时静默截断并消耗整条消息，没有显式截断选项；也没有独立的发送者/接收者等待队列及满队列背压。

### 中：信号量混合资源计数与广播事件

位置：`include/kernel/sem.h:16`、`kernel/ipc/sem.c:52`、`:93`、`:189`。

计数为 8 位，释放超过 255 时静默饱和。`sem_get()` 无返回值；无当前任务时即使没有令牌也直接返回。`sem_send_all()` 使所有现有等待者成功返回，却没有对应数量的令牌，它更像广播事件，不能沿用普通计数信号量的不变量。

VFS 文件位置及 FatFs 用信号量执行互斥，USB 传输和 shell join 用它等待完成，display/keyboard/LED 用它通知状态变化。迁移应按用途选择原语。

### 中：Endpoint 非阻塞和超时语义不完整

位置：`kernel/ipc/endpoint.c:166`、`:351`。

`NONBLOCK` 在没有接收者时返回 `-EAGAIN`；已有接收者时仍会进入回复等待。是否仅让发送阶段不阻塞必须明确，不能让同名参数暗示整个 RPC 不阻塞。回复和接收目前是先后调用，也不能宣称是一个已证明正确的原子组合操作。

### 中：Capability 传输与地址空间边界需要收紧

位置：`kernel/ipc/endpoint.c:39`、`kernel/syscall/syscall.c:265`。

Capability 逐个派生，失败后没有回滚；成功数被写回 tag，但成功句柄未压紧，可能出现第一个失败、第二个成功而 count 为 1 的布局。应预检、预留并整体提交，或明确返回部分成功的协议。

IPC syscall 当前直接使用用户指针，`buf_addr` 只是消息字段，不能被理解为接收方可安全解引用的跨地址空间指针。需要用户拷贝/访问检查边界；大数据使用显式授权的共享缓冲区。完整 VM 子系统重写不属于本次范围。

### 前置约束：现有 SMP 调度基础不能直接视为已完成

位置：`include/kernel/sched.h:56`、`kernel/sched/sched.c:26`、`kernel/timer.c:414`、各架构 `hal_smp_send_ipi()`。

调度禁止嵌套计数仍为全局普通整数；多 CPU 同时加减存在数据竞争，也会让一个 CPU 的锁影响其他 CPU 的调度/定时器检查。架构 IPI 函数目前为空。

此外，`timer_stop()` 仅摘除排队定时器；到期处理先摘链、解锁再调用回调，所以 stop 不能证明已派发的回调结束。等待代数、回调持有引用及安全回收必须共同设计，不能只加一次 stop。

## 3. 方案比较

| 方案 | 收益 | 代价和局限 | 建议 |
| --- | --- | --- | --- |
| A. 共用等待底座，按语义提供独立原语 | 原子完成规则一致；MCU 静态资源；SMP 对象间并行；调用意图清楚 | 涉及 task/timer/sched/cap 衔接，需分阶段迁移 | 推荐 |
| B. 全部统一为 Endpoint/通用 channel | 接口种类少，服务通信模型统一 | 中断通知、资源计数和本地短消息需要额外协议及存储，难兼顾 MCU 成本 | 不作为默认底座 |
| C. 保留现结构逐模块修补 | 初期改动少 | 继续重复维护超时、唤醒、退出及生命周期；很难证明组合正确 | 仅适合临时维护 |

## 4. 推荐架构方向（待批准）

### 4.1 共用等待与唤醒底座

- 每个任务有专用等待记录，携带对象引用、操作代数、截止时间和完成结果；等待节点、调度节点和延后唤醒节点互相独立。
- 对象锁内裁决 `WAITING → SUCCESS / TIMEDOUT / CLOSED / CANCELLED`，一个操作只能有一个终态。令牌、消息或通知数据的交付与 SUCCESS 提交在同一临界区完成。
- 准备等待时以一致顺序衔接任务状态和对象队列；唤醒先在对象锁内提交结果并固定任务引用，再解锁调用调度层。不能在持对象锁时反向获取任务锁。
- 调度层必须正确处理“刚准备睡眠便收到唤醒”，且不能让仍在原 CPU 执行的同一任务同时在另一 CPU 运行；不能仅以 pthread 条件变量替换整个生产等待逻辑来证明正确。
- 超时派发捕获不可变操作代数；回调、延后唤醒和待处理请求持有引用。过期回调不得作用于下次等待，也不得访问已回收的任务/对象。
- 抢占禁止计数改为每 CPU；主机测试采用线程局部 CPU 上下文。调度入队/远端唤醒通过统一接口，在主机验证 IPI 请求契约，硬件 IPI 后续实现。
- 普通 API 使用具名 timeout：建议 `NO_WAIT` 为 0、`FOREVER` 为独立保留值，有限超时转换为一次计算的绝对截止时间。迁移所有旧的 0=无限等待调用，禁止重试重置整个超时预算。

最终锁序、回调同步及任务回收协议在第一阶段规范中给出；本文的架构建议不等于这些细节已经实现或完成证明。

### 4.2 原语分工

| 原语 | 定义和边界 | 主要迁移对象 |
| --- | --- | --- |
| `msgq` | 每实例固定大小元素、有界 FIFO 环形缓冲；MPMC；显式容量；任务可超时等待，ISR 仅 no-wait；热路径不分配 | USB core/HID、消息测试 |
| `semaphore` | 32 位 count 和显式 limit；无 owner，不承担 PI；give 直接交付等待者；溢出显式报错 | 真正的资源令牌和有次数意义的生产/消费 |
| `completion` | 保存已发生的完成事件；单次完成可先于 wait；广播完成有独立语义；仅在无活动等待/回调时重置 | USB 传输完成、shell 子任务结束 |
| `notification` | 64 位按位 OR、同位重复事件合并；消费唤醒一个等待者；不是计数器或广播器 | UART、display/keyboard/LED 状态通知 |
| `endpoint` | 小消息同步 RPC；保留 64 字节 UAPI；显式一次性 reply 凭证；跟踪所有发送/回复等待事务 | 微内核服务调用 |
| `mutex` | owner 互斥和 PI；接入一致的等待完成/捐赠撤销规则 | VFS 文件位置、FatFs 串行化 |

消息 FIFO 与等待者选取分开定义。实时等待者建议按有效优先级选取、同级 FIFO；普通任务按明确的 FIFO 策略处理。阻塞期间的优先级变化须更新选择结果。第一版可用紧凑链表，只有测得必要时再增加索引；不承诺排队所有操作都是 O(1)。

固定大小消息传值；大块数据通过受控缓冲描述符及明确所有权传递。用户消息必须先拷到内核私有记录，禁止在自旋锁内触发用户地址异常或进行可能睡眠的分配。

关闭与销毁分离。关闭阻止新操作并完成所有等待，包括已交付请求的回复等待；动态对象在 Capability、在途调用、回调及唤醒引用全部释放后回收。静态对象由调用方在排空后回收存储。

Endpoint 的回复凭证独立于 badge 和 `nos_ipc_msg.token`，不挤占 64 字节布局。重复、过期、错服务器的回复必须失败。超时仅终止调用方等待，不承诺撤销服务端已经发生的副作用。PI 按请求记录和 mutex 共同聚合，完成/取消只撤销自身捐赠；不能照搬 seL4 MCS 的预算捐赠。

### 4.3 MCU 与 SMP 共用契约

MCU 默认调用方提供对象和消息缓冲区，容量及 RAM 可计算；ISR 操作有明确的非阻塞入口和拷贝上限，唤醒只请求调度。初始化时允许可选动态分配，消息热路径不进行堆分配。

SMP 使用对象级锁与 acquire/release 内存序，互不相关的 IPC 对象不共用一把全局锁。先覆盖一致性内存系统；非一致性缓存及 DMA 的可见性通过平台契约处理。第一版不引入通用无锁 MPMC 队列、RCU 或完整 futex/POSIX/SysV 兼容层。

USB 队列满时需逐类定义策略：可合并的周期/状态事件允许合并；SETUP、数据完成等有序事件不能静默丢弃，需要返回错误、背压或触发可诊断恢复。容量及溢出策略必须在迁移阶段结合具体控制器路径确定并测试。

## 5. 建议拆分与验收

分成三个依次进行的子项目，每个遵循 spec → plan → implementation：

1. 等待/超时/关闭/任务退出底座，必要的 per-CPU 抢占计数和调度衔接；接入 mutex 的交接及取消路径，保持已有 PI 功能。
2. 信号量、completion、notification 和有界消息队列；迁移 USB、UART、shell、显示/键盘/LED、VFS 和 FatFs，删除旧接口。
3. Endpoint 请求事务、reply 凭证、Capability 生命周期/传输和 syscall 用户拷贝边界；迁移服务与 libnos。

验收至少包括：

- 对真实生产原语编译的主机多线程测试，pthread 仅提供底层锁/阻塞执行环境。
- 用受控交错强制覆盖交付与超时、关闭与回复、退出与延后唤醒、旧回调与新等待、Capability 查找与销毁。
- 令牌守恒、消息不丢不重、FIFO/优先级策略、全局超时预算、重复回复拒绝、PI 全路径回收。
- 满队列 ISR 行为、非法上下文拒绝、无竞争时不强制切换、消息热路径零堆分配。
- `CONFIG_NR_CPUS=1` 及多 CPU 主机配置；可用时运行地址/未定义行为/线程 sanitizer，并明确平台工具限制。
- 32/64 位固定 64 字节 IPC ABI、权限衰减和传输失败回滚。
- 现有主机/Python/CMake/层次依赖测试、四个 MCU preset 构建及 STM32 QEMU 冒烟。
- 记录各配置的对象/TCB 大小、固件 RAM/ROM 增量及有界临界区成本；真实多核启动/IPI/缓存与硬件实时性属于后续专项。

## 7. 主流操作系统参考与采用边界

- [Linux 锁类型](https://docs.kernel.org/locking/locktypes.html)：采用 owner 互斥与无 owner 计数的区分，以及 CPU 本地控制与跨 CPU 锁的边界。
- [Linux completion](https://docs.kernel.org/scheduler/completion.html)：采用完成事件和先完成后等待语义，重视超时后的对象生命周期。
- [Linux semaphore 源码](https://github.com/torvalds/linux/blob/master/kernel/locking/semaphore.c)：参考锁内交付、锁外批量唤醒与等待结果仲裁；NOS 的限额和等待优先级是自身设计选择。
- [Linux wait queue 源码](https://github.com/torvalds/linux/blob/master/include/linux/wait.h)：参考条件检查、准备睡眠、唤醒及内存序的完整协议。
- [Zephyr 消息队列](https://docs.zephyrproject.org/latest/kernel/services/data_passing/message_queues.html)：参考固定大小、有界环形缓冲、多个等待者与 ISR no-wait。
- [Zephyr 信号量](https://docs.zephyrproject.org/latest/kernel/services/synchronization/semaphores.html)：参考 count/limit 和等待顺序。NOS 建议显式报告溢出，不照搬 Zephyr 的饱和策略。
- [Zephyr SMP](https://docs.zephyrproject.org/latest/kernel/services/smp/smp.html)：参考 UP/SMP 同语义和分离对象锁；本项目不以关本地中断替代跨 CPU 排他。
- [seL4 IPC](https://docs.sel4.systems/Tutorials/ipc.html)：参考小消息 rendezvous、badge 与一次性回复能力。
- [seL4 Notification](https://docs.sel4.systems/Tutorials/notifications.html)：参考位图事件合并及共享内存与控制消息分工。

这些是设计机制参考，不表示 NOS 已达到对应系统的安全证明、实时性或完整兼容性。
